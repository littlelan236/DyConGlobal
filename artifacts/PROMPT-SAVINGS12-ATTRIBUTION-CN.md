# 12-task token 节省：轨迹改善还是其他因素

分析时间：2026-10-21T23:55:25.031130+08:00。范围严格沿用本对话的历史 **12 个共同 Submitted、选中轨迹没有检测到 reasoning 内循环的任务**；不是 2026-10-21 verified80 的 52-task 表。没有启动 rollout 或 harness。重新读取并核验 24 条历史轨迹及补丁 SHA，token 总数完整复现原表。远程近期完成目录重构，原始证据从显式历史归档 `isolated/history-baseline-20261021/` 读取，未创建运行时旧路径 alias 或修改归档。

**判断：token 下降是真实记录，但“普遍、更正确地解决任务且节省 26.79%”尚不成立。主要表现为少数长轨迹更早提交、减少重复携带历史上下文；有效解题质量和评分器因果收益都还没有充分证明。** 有个别同补丁、同成功结果而更短的实例，可支持局部轨迹效率改善；大幅总体降幅则高度集中于未确认成功的任务。

## 1. 省下的是累计输入，输出没有变少

| 选择分支指标 | Baseline | Parallel | 变化 |
| --- | ---: | ---: | ---: |
| calls | 986 | 781 | -20.79% |
| prompt | 27,259,247 | 19,900,319 | -27.00% |
| completion | 206,344 | 207,918 | +0.76% |
| total tokens | 27,465,591 | 20,108,237 | -26.79% |

选择分支 total 从 27,465,591 降为 20,108,237，净减少 **7,357,354**。其中 prompt 减少 **7,358,928**，completion 反而增加 **1,574**。所以降幅主要不是模型少生成了 735 万 token，更不是压缩了这么多正常思考；它反映后续请求少重复带入历史上下文。

`prompt = calls × 平均每次 prompt`。本集合 calls 从 986 降到 781（−20.79%），平均每次 prompt 从 27,646.30 降到 25,480.56（-7.83%），两项相乘得到累计 prompt −27.00%。随着轨迹增长，晚期请求通常带着较长历史，少走后面的步骤会放大累计 prompt 的下降。这个放大本身是正常记账，但不能等价为同幅度的唯一信息量、实际 prefill 计算量或时延节省。

按 `P=N×μ` 的对称分解（对 calls 和均值两种替换顺序取平均），总体 prompt 差额中，calls 变化项为 -5,445,502.87，平均 prompt 变化项为 -1,913,425.13（均为 P−B）。这是算术分解，不是独立因果归因；每条轨迹的平均上下文也受其步数影响。

## 2. 97.69% 的净节省来自两个未确认成功的任务

| 任务 | calls（B→P） | 选择分支 total 节省 | 历史 harness（B→P） |
| --- | ---: | ---: | ---: |
| pylint-dev__pylint-4604 | 152 → 58 | 3,771,046 | completed/False → completed/False |
| pylint-dev__pylint-4551 | 164 → 98 | 3,416,426 | infra_error/None → completed/False |
| matplotlib__matplotlib-14623 | 93 → 88 | 669,638 | completed/True → completed/True |

前两个 pylint 任务合计减少 **7,187,472** tokens，占全体净节省 **97.69%**，也解释 205 次净调用减少中的 160 次（78.05%）。这是相对于正负相抵后的净节省占比，不是所有任务各自节省的占比。

- `pylint-dev__pylint-4604`：152→58 次调用，双方历史 harness 都 unresolved。Parallel 确实更短，但目前只能称“更少调用地得到一个仍未解决任务的提交”，不能称相同正确性的解题加速。
- `pylint-dev__pylint-4551`：164→98 次。Baseline 在最终提交命令中实际 `cat` 了源文件片段而非 git diff；历史 patch 是源文件文本，历史判分是 infra_error/null。Parallel 提交了 diff，但 harness 为 unresolved。这种比较混合了路径长度、提交格式与未确定质量，不能拿来验证“更快成功”。

删除头部任务只是敏感性检查，不是重新挑选有利 cohort：

| 范围 | 任务数 | calls 变化 | prompt 变化 | completion 变化 | 选择分支 total 变化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全部 12 个 | 12 | -20.79% | -27.00% | +0.76% | -26.79% |
| 排除节省最多的 2 个 | 10 | -6.72% | -1.20% | +14.81% | -1.05% |
| 排除节省最多的 3 个 | 9 | -6.93% | +3.62% | +18.28% | +3.76% |
| 双方 harness 均 resolved | 4 | -0.80% | -7.47% | -1.60% | -7.42% |
| 双方 harness 均 unresolved | 4 | -29.66% | -29.57% | +0.66% | -29.36% |

9/12 个任务的选择 total 下降，3/12 上升；任务相对变化中位数是 −20.64%，所以并非只有两个任务在变短。但 **26.79% 的聚合幅度**由头部任务主导：去掉前两个只剩 −1.05%，再去掉第三个变为 +3.76%。按任务成对 bootstrap 10,000 次，聚合 total 变化的描述性 95% 区间约 **−51.59%～+4.94%**，跨过 0。该区间只反映这 12 个任务的分布不稳定，不能替代多 seed 试验或完整 benchmark 推断。

## 3. 什么证据支持确实少走了部分弯路

在相同记录口径下，精确重复的命令超出首次出现部分从 **134→67**，工具非零返回码从 **143→75**，测试相关命令提及数从 **303→254**，工具输出字符从 **989,348→886,493**。这些与较短路径相容，但单次重复测试可能有意义，非零返回可能是正常测试失败/搜索无命中，测试减少也可能是验证不足；这些代理指标不能单独给 token 节省贴上“有效优化”标签。

具体例子：`pylint-dev__pylint-4551` 的 Baseline `cat classes.dot` 出现 19 次，同一 pyreverse typehints 命令出现 10 次，edge_cases 命令出现 9 次；Parallel 仍有重复，但更少。这说明剔除“单次 reasoning 内循环”并没有剔除跨 step 的反复检查和试错。因此，本表剩余节省可能包含减少动作级重复，而不是减少正常 reasoning。

较强的局部正例是 `pytest-dev__pytest-10081`：双方历史 harness 都 resolved，最终补丁 SHA **完全相同**（`b37f66e9dcb2759c5e9af83989e08d2024bb52d55e55fdbc2b1740de3882b372`），calls 49→34，选择 total 739,308→389,078（−47.37%）。这支持该对历史轨迹用更少步骤得到了同一已验证补丁，但由于 seed/精度等设置不同，仍不能确定收益由 Ridge 选择单独造成。

相反，`astropy__astropy-8707` 双方也都 resolved，但 calls 63→88，选择 total 1,291,622→2,027,116（+56.94%），说明不是对成功任务普遍优化。双方都 resolved 的 4 个任务合计仅 249→247 次调用（−0.80%），选择 total −7.42%。这个子集过小，而且按运行结果筛选存在选择偏差，只作为质量一致性核查。

## 4. 是否只是隐藏了上下文、改了预算或少算了用量

本次核对可以排除或收窄以下解释：

- **统计漏算**：每条轨迹按顶层 response id 去重，calls 和选中 usage 逐任务匹配原始汇总；全分支与赢家分开，没有用赢家代替全部实际生成开销。
- **换了更短初始提示**：12/12 个配对任务的首请求 prompt 相同；轨迹冻结的 system/instance 模板相同。
- **显式改了工具输出截断模板**：两侧 observation 模板逐字相同，均在原始工具输出达到 10,000 字符后只保留前后各 5,000 字符。工具输出自然不同仍会影响上下文，不能把差额全部叫作有效压缩。
- **更小的输出/步数上限**：两侧冻结 agent step limit=250，max_tokens=81,920，temperature/top_p 一致；并非 Parallel 换了更小预算强制停止。
- **明显的中途上下文重置**：24 条轨迹的逐请求 prompt 长度都没有下降，未见上下文突然缩短的信号。结合模板相同，当前没有积极证据支持“靠上下文清空制造降幅”；仅凭长度单调不能严格证明任何内容都未被替换或截断。

Baseline BF16/seed0、Parallel FP16/seed42+branch，以及历史并发和 vLLM 版本存在差异。这些能改变采样、动作路径和输出长度；不是严格的“只改评分选择”对照。工具错误/测试结果也随路径与环境状态变化，工具错误减少尚不能独立归因于轨迹规划更好。

## 5. Submitted、正确性与真实计算成本要分别判断

这 12 个任务的原表历史 harness 状态：Baseline resolved=4、unresolved=6、unknown/infra=2；Parallel resolved=5、unresolved=6、unknown/infra=1。unknown 不按失败计算，也未重跑评测或用新版目录的其他评测覆盖历史证据。没有观察到该历史共同子集中已确认成功→已确认失败的配对，但两个主要节省来源都没有证实同等成功质量。

`Submitted` 只是轨迹触发了提交，不保证补丁合法或修复完成；最低剩余量也可能偏爱接近一个未成功提交的状态。旧 predictor 的目标是 close 后的 submission 剩余 reasoning 数量，不能把它直接当作修复正确性 reward。排除 Baseline 循环任务与只取共同 Submitted 也都是运行后筛选，不能据此代表原始完整 cohort 的算法收益。

更直接的成本检查是：全分支 total **27,465,591→80,742,113（+193.98%）**，全分支 completion **206,344→1,140,837（+452.88%）**。12 个任务只保证两侧选中轨迹没检出 reasoning 内循环，Parallel 的落选候选仍有循环，包含此前核验的 4 条各 81,920-token reasoning 循环。此表不能证明端到端推理算力下降。prompt 是逻辑输入 token，APC 命中的历史 token 不等于重新 prefill；旧 Baseline 无逐请求 cache-miss 计数，无法将 27.00% 逻辑 prompt 降幅换算成实际计算节省。

## 6. 当前应怎样表述，以及怎样进一步验证

可以写：**“在剔除选中轨迹单次 reasoning 循环的 12 个共同 Submitted 任务上，Parallel 赢家轨迹的逻辑输入累计减少 27.00%，调用减少 20.79%；输出没有减少。净节省高度集中于两个未确认成功的长任务。个别同补丁、同成功的配对支持局部轨迹效率改善，但尚未证明普遍且保持质量的解题效率提升。”**

若要区分选择器真实作用，下一轮应在同一 B=4、相同精度/runtime/预算/资格过滤下比较 **有效非循环候选随机选择 vs 最低分选择**，以完整预先冻结 cohort、多个 seed 报告 harness resolved、正确补丁完成成本和全部分支实际开销。对失败更早提交、无效补丁、infra 分别列示；共同 Submitted 仅作附表。同时记录生成/工具/评分时间和 cache-miss prompt；对主要节省案例核查修改与验证阶段，而不是只按少几步定义优化。本次没有启动此新实验。
